# 第 17 节：理论到开发映射复盘

## 1. 学习目标

本节目标是把前面理论收束到后续开发中，明确每个概念会落到哪些代码、表、接口和测试里。

## 2. 基础概念到目录结构

理论：

```text
LLM = 推理和生成能力
Agent = 有职责的智能执行单元
Workflow = 多 Agent 执行流程
Tool Calling = Agent 调用真实系统能力
```

落到代码：

```text
python-agent-service/app/agents/
python-agent-service/app/services/
python-agent-service/app/tools/
python-agent-service/app/schemas/
```

对应：

- `agents/`：5 个 Agent。
- `services/`：Supervisor 编排逻辑。
- `tools/`：Java API 调用封装。
- `schemas/`：Pydantic 输入输出模型。

## 3. 多 Agent 协同到代码文件

第一期 5 个 Agent 会落成：

```text
supervisor_agent.py
product_planning_agent.py
image_creative_agent.py
inventory_purchase_agent.py
order_fulfillment_agent.py
```

每个 Agent 都要有：

- 输入 Schema。
- 输出 Schema。
- 执行方法。
- 错误处理。
- 测试。

## 4. 结构化输出到 Pydantic Schema

核心 Schema：

```text
ProductContext
InventoryContext
OrderContext
ProductPlan
ImagePlan
InventoryPlan
FulfillmentPlan
OperationPlanResult
AgentRunRecord
```

作用：

- 约束 Agent 输出。
- 让 Supervisor 汇总。
- 让 Java 解析。
- 让数据库保存。
- 让测试断言。

## 5. Tool Calling 到 API

Python 工具层：

```text
python-agent-service/app/tools/java_api_client.py
```

Java Tool API：

```text
GET  /api/tools/products/{productId}
GET  /api/tools/inventories/{productId}
GET  /api/tools/orders/{orderId}
POST /api/tools/operation-plans
POST /api/tools/agent-runs
```

开发原则：

```text
Python 不能直接写 PostgreSQL
必须通过 Java API 查询和保存业务数据
```

## 6. 可追踪性到数据表和接口

Java 表：

```text
operation_plans
agent_runs
```

Java 查询 API：

```text
GET /api/operation-plans/{planId}
GET /api/operation-plans/{planId}/agent-runs
```

一次完整执行至少产生：

```text
1 条 operation_plans
5 条 agent_runs
```

## 7. Java/Python 边界到模块职责

Java 负责：

```text
products
inventories
orders
operation_plans
agent_runs
业务 API
Tool API
Python Agent Client
```

Python 负责：

```text
Agent Schema
Agent 执行
Supervisor 编排
Tool Client
Agent API
```

## 8. 大框架小闭环到第一期范围

第一期必须有：

```text
Python 服务

PostgreSQL
5 个 Agent
5 张表
三组 API
端到端执行
```

第一期不做：

```text
支付
退款
物流
售后
真实图片生成
复杂权限
多店铺
消息队列
```

## 9. 人机协同到字段

第一期先落到：

```text
manual_review_required
NEEDS_REVIEW

```

后续再扩展：

```text
manual_reviews

```

```

Entity / Repository

```

## 11. 上下文到 Agent 输入

Product Planning Agent 输入：

```text
ProductContext
```

Image Creative Agent 输入：

```text
ProductContext + ProductPlan.selling_points
```

Inventory & Purchase Agent 输入：

```text
InventoryContext + Order.quantity
```

Order Fulfillment Agent 输入：

```text
OrderContext + InventoryContext
```

## 12. 记忆管理到第一期实现

第一期记忆：

```text
operation_plans = 最终执行结果记忆
agent_runs = 每个 Agent 执行过程记忆
```

第一期不做：

```text
共享知识库
向量库
Agent 私有记忆
RAG
```

## 13. LangGraph 到节点设计

后续可以映射为：

```text
OperationPlanState
product_planning_node
image_creative_node
inventory_purchase_node
order_fulfillment_node
summary_node
```

第一期只做固定流程，不急着做复杂动态路由。

## 14. 错误出口到结构化 errors

第一期错误可先落到：

```text
OperationPlanResult.errors
agent_runs.error_message
operation_plans.status
```

错误类型：

```text
INPUT_INVALID
BUSINESS_RISK
AGENT_FAILED
AGENT_SCHEMA_INVALID
TOOL_API_FAILED
PYTHON_SERVICE_FAILED
PERSISTENCE_FAILED
WORKFLOW_INTERRUPTED
UNKNOWN_ERROR
```

## 15. 第一期开发展开规则

开发时遵守：

```text
先 Schema，后 Agent
先规则模板，后 LLM
先固定 Workflow，后动态路由
先 Agent 级追踪，后 Tool 级追踪
先 Java 业务事实，后知识库增强
先小闭环，后大功能
错误要分出口，不要统一糊掉
```

## 16. 面试表达

可以这样讲：

> 我这个项目不是简单调大模型 API，而是按企业级 Agent 系统设计。Python 侧使用多 Agent 协同，基于 Supervisor 模式组织商品规划、图片创意、库存补货和订单履约 4 个子 Agent；每个 Agent 都有明确职责、最小上下文、结构化输出和执行记录。Java 侧作为业务主系统，保存商品、库存、订单、运营建议和 agent_runs，并通过 Tool API 提供受控业务能力。第一期采用大框架、小闭环策略，先用规则和模板跑通 Schema、Workflow、Tool Calling、Trace 和错误出口，后续再接入 LLM、分类知识库、动态路由和更复杂的人机协同。

理论学习的目的不是懂概念，而是指导开发取舍。
