# 第 06 节：为什么第一期先用规则和模板

## 1. 学习目标

本节目标是理解为什么第一期不急着接入真实大模型，而是先用规则和模板实现 5 个 Agent 的最小能力。

第一期重点是：

```text
框架是否成立
边界是否清楚
数据是否流转
结果是否可追踪
```

不是模型回答得多漂亮。

## 2. 一开始接 LLM 的风险

如果一开始就接真实 LLM，容易被这些问题干扰：

- API Key 配置。
- 模型响应慢。
- 输出格式不稳定。
- 网络异常。
- 调用费用。
- Prompt 调不准。
- 同一个输入多次输出不一致。

这些问题会让我们还没理解架构，就陷入调模型细节。

## 3. 规则和模板可以先验证架构

例如库存 Agent 第一版可以用规则：

```text
available_stock = current_stock - reserved_stock

如果 available_stock < safe_stock_threshold:
    should_restock = true
    restock_priority = HIGH
否则:
    should_restock = false
```

这足够验证：

- Schema 是否正确。
- Supervisor 是否能调用。
- Java 是否能保存。
- `agent_runs` 是否能记录。
- 测试是否能覆盖。

## 4. 5 个 Agent 的第一版实现策略

### 4.1 Supervisor Agent

第一版用固定规则编排：

```text
调用 Product Planning
调用 Image Creative
调用 Inventory & Purchase
调用 Order Fulfillment
汇总结果
```

### 4.2 Product Planning Agent

第一版用模板生成标题、卖点和详情文案。

后续再用 LLM 增强文案质量。

### 4.3 Image Creative Agent

第一版用模板生成主图、场景图、营销图提示词。

后续再接入 LLM 或图片生成模型。

### 4.4 Inventory & Purchase Agent

第一版规则优先。

后续可以加入销量预测和 LLM 解释。

### 4.5 Order Fulfillment Agent

第一版规则优先。

例如：

```text
未付款 -> 不能出货
地址不完整 -> 需要人工确认
可用库存 < 订单数量 -> 库存不足
否则 -> 可出货
```

## 5. 先规则后 LLM 更容易测试

LLM 输出具有不确定性，不适合第一期稳定测试。

第一期我们需要稳定断言：

```text
should_restock == true
restock_priority == "HIGH"
inventory_status == "RISK"
```

规则实现更适合验证框架和测试。

## 6. LLM 是增强能力，不是系统地基

第一期系统地基是：

```text
Schema
Workflow
Tool API
Trace
Java/Python 边界
```

LLM 后续作为增强能力加入。

这样即使没有 LLM，项目也能跑通；LLM 失败时也可以降级到模板。

## 7. 哪些部分不应完全交给 LLM

以下内容应由规则和 Java 系统控制：

- 是否已付款。
- 库存是否足够。
- 地址是否完整。
- 是否允许真实发货。
- 是否扣减库存。
- 是否退款。
- 是否修改价格。

LLM 可以解释、建议、总结，但不能绕过确定性规则。

## 8. 面试表达

可以这样讲：

> 第一阶段我没有一上来就把所有 Agent 接入大模型，而是先用规则和模板实现 5 个 Agent 的最小能力。这样可以优先验证多 Agent 编排、结构化输出、Java/Python 服务边界、Tool API 和执行追踪。等框架稳定后，再把内容生成类 Agent 逐步替换为 LLM 实现，把库存和履约类 Agent 保持规则为主、LLM 辅助解释。

## 9. 小结

第一期先用规则和模板，是为了搭稳多 Agent 框架、Schema、Workflow、Tool API 和 Trace。

LLM 不应该一开始就成为系统地基，而应该作为后续增强能力逐步接入。
