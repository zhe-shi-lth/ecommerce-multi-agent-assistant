# 第 09 节：人机协同与人工确认

## 1. 学习目标

本节目标是理解企业级 Agent 系统为什么不能盲目全自动，以及本项目如何用 `manual_review_required` 和 `NEEDS_REVIEW` 建立人机协同边界。

## 2. 人机协同不是简单兜底

人机协同不是：

```text
AI 不行了，就让人处理
```

更准确是：

```text
Agent 负责分析和建议
人负责判断和授权
系统负责记录和执行边界
```

## 3. 企业 Agent 不能一上来全自动

电商场景中的高风险动作包括：

- 自动改商品价格。
- 自动发货。
- 自动退款。
- 自动下采购单。
- 自动修改库存。
- 自动发布商品。
- 自动使用生成图片上线。

这些动作可能造成真实业务损失。

第一期只做：

```text
Agent 生成建议
Java 保存结果
用户查看
需要时人工确认
```

## 4. 哪些场景需要人工确认

商品侧：

- 商品信息缺失。
- 销售价低于成本价。
- 文案存在夸大功效。
- 图片提示词存在侵权或敏感风险。

库存侧：

- 建议补货数量过大。
- 库存风险高。
- 最近销量异常。
- 采购周期过长。

订单侧：

- 订单未付款。
- 收货地址不完整。
- 可用库存不足。
- 订单数量异常。
- Agent 判断冲突。

## 5. manual_review_required 的作用

`manual_review_required` 表示：

```text
当前结果不能完全自动执行，需要人看一下。
```

例如：

```json
{
  "can_ship": false,
  "fulfillment_status": "NEEDS_REVIEW",
  "risk_flags": ["订单未付款", "收货地址不完整"],
  "manual_review_required": true,
  "next_order_status": "NEEDS_REVIEW"
}
```

Supervisor 汇总后，最终结果也应该标记人工确认。

## 6. Agent、Java、人三方分工

```text
Agent：分析者
Java 系统：记录者和边界控制者
人：最终授权者
```

低风险场景：

```text
Agent 判断可以出货
Java 保存 READY_TO_SHIP
用户查看确认
```

高风险场景：

```text
Agent 判断需要人工确认
Java 保存 NEEDS_REVIEW
人处理后续动作
```

## 7. 人工确认后后续可记录什么

后续可扩展：

- 谁确认。
- 什么时候确认。
- 确认结果。
- 是否采纳 Agent 建议。
- 人工修改了什么。
- 原因是什么。

第一期先不建完整人工确认表，只用字段表达协同意识。

## 8. 人机协同依赖可追踪性

人工确认必须能看到：

- Agent 输入是什么。
- 每个 Agent 输出是什么。
- 哪个 Agent 认为有风险。
- 为什么需要人工确认。
- 最终建议是什么。

所以人机协同依赖：

```text
trace_id
agent_runs
operation_plans
```

## 9. 面试表达

可以这样讲：

> 在这个项目里，我没有让 Agent 直接执行所有业务动作，而是设计了人机协同边界。Agent 负责分析商品、图片、库存和订单，输出结构化建议和风险标记；Java 系统负责保存结果和流程状态；当出现未付款、地址不完整、库存不足、图片风险或补货数量异常时，系统会将 manual_review_required 标记为 true，进入人工确认。

## 10. 小结

人机协同不是 Agent 不够强，而是企业级 Agent 必须可控。

第一期用 `manual_review_required` 和 `NEEDS_REVIEW` 建立人机协同意识，后续再扩展完整人工确认流程。
