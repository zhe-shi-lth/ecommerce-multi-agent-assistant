# 系统现状与用户使用手册

更新时间：2026-08-16

## 一、系统现在做到什么程度

当前系统已经不是单纯的 Agent 演示，而是一套具备业务主链路、组织权限和生产保护机制的电商运营后台。除第三方官方 API 字段映射、商家授权联调和真实生产环境基础设施外，内部业务闭环基本完成。

### 1. 已完成的业务能力

- 线 1 内容生产：选择店铺、平台和商品，填写 Content Brief 及图片/视频/文案要求，生成图片、文案和视频，经过人工审核后形成运营计划并进入发布任务。
- 三平台并行：小红书、淘宝、抖音可同时存在，各平台分别生成内容、审核和发布，不互相阻塞。
- 真实生成门控：文案、图片、视频缺少模型 Key 或调用失败时直接提示，不生成假数据。
- 发布任务：具备统一适配器、幂等键、并发认领、失败重试、超时识别、人工重试和对账状态。
- 线 2 订单履约：订单拉取、未付款、地址不全、库存不足、人工复核、库存预留、原子扣减、发货和售后状态流转已经具备。
- 采购补货：供应商管理、采购申请、运营计划审批、下单、待入库、分批收货、短收关闭、正式入库、成本和采购运费记录已经闭环。
- 库存安全：订单预留与扣减使用数据库并发控制，避免并发超卖和负库存。
- 数据与审计：关键状态变更均有业务审计、库存流水、采购收货记录和 Agent 执行 trace。

### 2. 已完成的用户与企业体系

- 公司/租户、公司下店铺、用户加入公司。
- 超级管理员只负责平台开户；企业老板管理店铺；员工权限按店铺独立多选分配。
- 登录后 JWT 携带当前公司、店铺和权限集合；每次请求重新校验成员有效性。
- 商品、订单、供应商、库存、采购、运营计划、媒体、平台任务和审计按公司/店铺隔离。
- 超级管理员创建企业并指定老板，不加入任何企业；老板创建多个店铺，并将员工加入一个或多个店铺。
- 同一用户可属于多个企业，并在侧边栏切换企业/店铺。
- AI 能力设置按企业保存：文案、图片、视频、审核和监控配置由企业老板统一维护，旗下店铺共用。
- 淘宝、抖音、小红书平台凭证按店铺加密保存，前端只显示配置状态和掩码，不读取明文。
- 旧版本按“企业+店铺”保存的 AI 设置，在企业首次访问设置中心时自动迁移到企业级文件。
- 设置中心只对超级管理员和企业老板开放；平台授权也只允许这两类账号管理。
- 操作审计记录真实用户；定时任务明确记录为系统操作。

### 3. 尚未完成或需要真实环境才能完成

- 小红书、淘宝、抖音官方开放平台的 OAuth 授权、真实请求/响应字段映射和商家联调；当前适配器保持失败闭合，不把 TODO 当成真实成功。
- 平台真实发布、订单拉取、地址查询、发货物流单号回传、退款/售后同步的商家联调。
- 具体图像、视频、文本模型供应商的生产账号、额度、回调和内容安全策略联调。
- HTTPS 域名、云服务器、生产数据库、对象存储、集中日志、告警通知、定时备份和灾备策略。
- 大规模数据量下的容量压测、平台限流压测和真实商家试运行验收。

因此，当前更准确的定位是：**内部业务和生产骨架已完成，进入“外部 API 接入与商家试运行”阶段**。接入 API 并不只填 Key，还要完成平台字段映射、OAuth 回调、错误码处理和真实账号验收。

## 二、接入所有 API 后，用户如何使用

### 1. 平台运营方开通系统

1. 超级管理员登录系统，在“组织与成员”创建一家企业并填写老板邮箱和初始密码。
2. 老板首次登录后创建一家或多家店铺。
3. 在生产环境配置 HTTPS、数据库、对象存储、JWT 密钥、服务密钥和凭证加密密钥。

### 2. 商家老板初始化企业

1. 老板登录后，在“组织与成员”创建实际经营店铺。
2. 添加员工，选择员工加入的一个或多个店铺，并多选具体权限。
3. 在“设置中心”配置企业级文案、图片、视频模型账号；旗下店铺共用这些 AI 能力配置。
4. 进入具体店铺配置该店铺的小红书、淘宝、抖音 OAuth 授权；不同店铺凭证互不共用。
5. 建立供应商、商品、初始库存、安全库存、采购周期和运费规则。

### 3. 运营人员完成新品内容与发布

1. 在“商品”维护商品基础资料、售价、成本、品类和目标人群。
2. 进入“新品上架”，选择当前店铺、目标商品和一个或多个平台。
3. 填写统一 Content Brief，并分别填写图片、视频、文案要求。
4. 按需上传参考图片，生成商品图片；生成的视频可以引用已确认图片作为素材。
5. 分别检查图片、视频和平台文案，不满意则驳回重做。
6. 提交运营计划，老板在“运营计划”审核新品上架计划。
7. 审核通过后触发各平台发布任务。任务失败不会显示假成功，可在详情查看原因并人工重试或对账。

### 4. 系统自动拉单并完成履约

1. 平台适配器按店铺拉取真实订单并幂等入库，避免重复订单。
2. 系统自动识别未付款、地址不全、库存不足和需人工复核订单。
3. 已满足条件的订单预留库存；并发订单通过数据库原子操作避免超卖。
4. 地址补全或付款完成后，订单自动重新进入可处理状态。
5. 仓库人员核对商品并填写物流公司、运单号，点击发货。
6. 系统调用对应店铺的平台发货 API 回传物流信息，并记录任务和审计。
7. 平台失败时保留本地状态和外部结果快照，进入重试或人工对账，不重复发货。

### 5. 采购人员完成补货

1. 先在“进货商家”建立供应商资料。
2. 库存预警产生补货建议，或采购人员主动发起采购申请。
3. 申请中填写供应商、商品、数量、单价、采购运费、预计到货日和备注。
4. 老板在“运营计划”的采购 Tab 审批。
5. 审批通过后，采购人员标记已下单和待入库。
6. 仓库按实际到货分批收货；全部到货后入库，短收则按原因关闭。
7. 系统增加库存、计算落地单位成本，并记录收货单、库存流水和真实操作人。

### 6. 老板查看经营和风险

1. 在“销售监控”查看销售、库存水位和待办预警。
2. 在订单和运营计划详情查看平台任务、失败原因和重试状态。
3. 在审计记录中追踪谁在什么企业、店铺对哪个业务对象做了什么操作。
4. 在侧边栏切换企业/店铺；切换后所有业务列表和平台凭证自动进入对应租户上下文。

## 三、角色使用边界

| 角色 | 主要职责 |
| --- | --- |
| 超级管理员 | 创建企业、平台级用户监控、处理系统级配置 |
| 老板 | 管理店铺、员工、权限、平台凭证和企业业务 |
| 店铺员工 | 只可使用老板分配到当前店铺的权限，可加入多个店铺 |

## 五、本地开发启动

```powershell
# 1. PostgreSQL
docker compose up -d postgres

# 2. Java，工作目录 java-service
.\mvnw.cmd spring-boot:run

# 3. Python，工作目录 python-agent-service
uv run fastapi dev app/main.py --host 0.0.0.0 --port 8000

# 4. 前端，工作目录 frontend
npm run dev -- --host 0.0.0.0
```

开发地址：`http://localhost:5173/`。默认超级管理员为 `admin@shop.local / admin123`，仅用于本地开发，生产环境必须删除默认账号或修改密码。
