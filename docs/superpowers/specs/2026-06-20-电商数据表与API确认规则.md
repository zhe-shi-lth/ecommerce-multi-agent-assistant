# 电商超级个体多 Agent 运营助手数据表与 API 确认规则

## 1. 文档目的

本文档用于约束第一阶段的数据表和 API 设计，保证后续开发围绕“大框架、小闭环”的目标推进。

第一阶段核心目标：

- 让 5 个 Agent 全部参与一次完整业务流。
- 让 Java 与 Python 的服务边界跑通。
- 让商品、库存、订单、运营建议和 Agent 执行记录能够落库。
- 先保证结构完整，再逐步增强业务细节。

## 2. 第一阶段数据表确认原则

第一阶段只建支撑闭环所需的数据表，不提前设计完整电商平台。

建表原则：

- 一张表必须服务于第一阶段闭环。
- 一张表必须能被 Java 业务 API、Python Agent 或执行记录使用。
- 不为了“以后可能用到”提前建表。
- Agent 输出必须能落到结构化字段或 JSON 字段中。
- Agent 执行过程必须可追踪，包括输入、输出、状态、耗时和错误。
- 第一阶段允许部分字段简化，后续再拆表或细化。

第一阶段暂不建：

- 供应商表。
- 采购单表。
- 物流表。
- 售后表。
- 店铺表。
- 平台账号表。
- 图片素材表。
- 用户权限细分表。

这些表进入后续增强阶段再设计。

## 3. 第一阶段确认数据表

### 3.1 products 商品表

用途：

- 保存商品基础信息。
- 给 Product Planning Agent 和 Image Creative Agent 提供输入。

核心字段：

- `id`：商品 ID。
- `name`：商品名称。
- `category`：商品类目。
- `description`：商品基础描述。
- `cost_price`：成本价。
- `sale_price`：销售价。
- `target_audience`：目标人群。
- `usage_scenario`：使用场景。
- `status`：商品状态。
- `created_at`：创建时间。
- `updated_at`：更新时间。

第一阶段状态：

- `DRAFT`：草稿。
- `ANALYZED`：已分析。
- `NEEDS_REVIEW`：需要人工确认。

### 3.2 inventories 库存表

用途：

- 保存商品库存和补货判断所需数据。
- 给 Inventory & Purchase Agent 提供输入。

核心字段：

- `id`：库存记录 ID。
- `product_id`：商品 ID。
- `current_stock`：当前库存。
- `reserved_stock`：已占用库存。
- `safe_stock_threshold`：安全库存阈值。
- `purchase_cycle_days`：采购周期天数。
- `sales_last_7_days`：最近 7 天销量，第一阶段可以手填或模拟。
- `inventory_status`：库存状态。
- `created_at`：创建时间。
- `updated_at`：更新时间。

第一阶段状态：

- `ENOUGH`：库存充足。
- `LOW`：库存偏低。
- `RISK`：存在缺货风险。

### 3.3 orders 订单表

用途：

- 保存模拟订单。
- 给 Order Fulfillment Agent 提供输入。

核心字段：

- `id`：订单 ID。
- `product_id`：商品 ID。
- `quantity`：购买数量。
- `status`：订单状态。
- `address_complete`：收货地址是否完整。
- `paid`：是否已付款。
- `manual_review_required`：是否需要人工确认。
- `fulfillment_suggestion_status`：出货建议状态。
- `created_at`：创建时间。
- `updated_at`：更新时间。

第一阶段状态：

- `PENDING_ANALYSIS`：待分析。
- `READY_TO_SHIP`：可出货。
- `INSUFFICIENT_STOCK`：库存不足。
- `NEEDS_REVIEW`：需要人工确认。

### 3.4 operation_plans 运营建议表

用途：

- 保存 Supervisor Agent 汇总后的最终运营建议。
- 支撑用户查询一次完整分析结果。

核心字段：

- `id`：运营建议 ID。
- `trace_id`：执行链路 ID。
- `product_id`：商品 ID。
- `order_id`：订单 ID。
- `product_plan_json`：商品运营建议 JSON。
- `image_plan_json`：图片创意建议 JSON。
- `inventory_plan_json`：库存补货建议 JSON。
- `fulfillment_plan_json`：订单履约建议 JSON。
- `final_summary`：最终摘要。
- `manual_review_required`：是否需要人工确认。
- `status`：执行结果状态。
- `created_at`：创建时间。
- `updated_at`：更新时间。

第一阶段状态：

- `SUCCESS`：执行成功。
- `PARTIAL_FAILED`：部分 Agent 失败。
- `FAILED`：执行失败。

### 3.5 agent_runs Agent 执行记录表

用途：

- 保存每个 Agent 的执行过程。
- 支撑调试、追踪、面试演示和后续可观测性增强。

核心字段：

- `id`：执行记录 ID。
- `trace_id`：执行链路 ID。
- `operation_plan_id`：运营建议 ID。
- `agent_name`：Agent 名称。
- `input_json`：Agent 输入 JSON。
- `output_json`：Agent 输出 JSON。
- `status`：执行状态。
- `duration_ms`：执行耗时。
- `error_message`：错误信息。
- `started_at`：开始时间。
- `finished_at`：结束时间。

第一阶段 Agent 名称：

- `SUPERVISOR_AGENT`。
- `PRODUCT_PLANNING_AGENT`。
- `IMAGE_CREATIVE_AGENT`。
- `INVENTORY_PURCHASE_AGENT`。
- `ORDER_FULFILLMENT_AGENT`。

第一阶段状态：

- `SUCCESS`：成功。
- `FAILED`：失败。
- `SKIPPED`：跳过。

## 4. API 确认原则

第一阶段 API 分三组：

1. 用户或前端调用 Java 的业务 API。
2. Java 调用 Python 的 Agent API。
3. Python 工具层调用 Java 的 Tool API。

API 设计原则：

- 第一阶段只做闭环所需 API。
- Java 是业务数据和状态的主系统。
- Python Agent 不直接操作数据库。
- Python Agent 通过 Java Tool API 查询和保存业务数据。
- Java 调 Python 只保留一个统一 Agent 分析入口。
- 所有跨服务请求都要携带或返回 `trace_id`。
- 所有 Agent 输出都必须结构化。
- 第一阶段不做删除 API。
- 第一阶段不做复杂分页、搜索和筛选。
- 第一阶段不做完整认证授权，后续增强。

## 5. 用户或前端调用 Java 的业务 API

这些 API 面向使用者或后续前端页面。

### 5.1 商品 API

```text
POST /api/products
GET  /api/products/{productId}
```

用途：

- 创建商品。
- 查询商品详情。

### 5.2 库存 API

```text
POST /api/inventories
GET  /api/inventories/{productId}
```

用途：

- 创建或初始化商品库存。
- 按商品 ID 查询库存。

### 5.3 订单 API

```text
POST /api/orders
GET  /api/orders/{orderId}
```

用途：

- 创建模拟订单。
- 查询订单详情。

### 5.4 运营建议 API

```text
POST /api/operation-plans
GET  /api/operation-plans/{planId}
GET  /api/operation-plans/{planId}/agent-runs
```

用途：

- 触发一次多 Agent 运营分析。
- 查询最终运营建议。
- 查询每个 Agent 的执行记录。

## 6. Java 调 Python 的 Agent API

第一阶段 Python 只暴露一个统一入口。

```text
POST /agent/ecommerce/operation-plan
```

用途：

- Java 将商品、库存、订单和触发类型发送给 Python。
- Python 执行 5 Agent 协同流程。
- Python 返回 `OperationPlanResult`。

请求数据：

- `product`：商品上下文。
- `inventory`：库存上下文。
- `order`：订单上下文。
- `trigger_type`：触发类型，第一阶段固定为 `GENERATE_OPERATION_PLAN`。

响应数据：

- `trace_id`：执行链路 ID。
- `product_plan`：商品运营建议。
- `image_plan`：图片创意建议。
- `inventory_plan`：库存补货建议。
- `fulfillment_plan`：订单履约建议。
- `final_summary`：最终摘要。
- `manual_review_required`：是否需要人工确认。
- `errors`：错误列表。

## 7. Python 调 Java 的 Tool API

这些 API 不直接面向用户，而是给 Python Agent 工具层使用。

### 7.1 查询工具

```text
GET /api/tools/products/{productId}
GET /api/tools/inventories/{productId}
GET /api/tools/orders/{orderId}
```

用途：

- Agent 查询商品。
- Agent 查询库存。
- Agent 查询订单。

### 7.2 保存工具

```text
POST /api/tools/operation-plans
POST /api/tools/agent-runs
```

用途：

- 保存最终运营建议。
- 保存每个 Agent 的执行记录。

## 8. 第一阶段不做的 API

第一阶段不做：

- `DELETE` 类 API。
- 批量导入 API。
- 复杂分页查询。
- 多条件搜索。
- 用户登录和权限 API。
- 支付 API。
- 退款 API。
- 物流 API。
- 售后 API。
- 店铺平台授权 API。
- 图片生成 API。

这些 API 等 Agent 框架稳定后，再按阶段增加。

## 9. 后续开发规则

后续新增表或 API 时，必须先回答 5 个问题：

1. 这个表或 API 是否服务第一阶段闭环？
2. 哪个 Agent 会读取或写入它？
3. 它是否需要进入 Agent 执行记录或 trace 链路？
4. 它是否可以先用 JSON 字段或轻量状态代替？
5. 如果不做它，第一阶段闭环是否仍然能跑通？

如果第 5 个问题答案是“能跑通”，第一阶段默认不做。

## 10. 当前确认状态

已确认：

- 第一阶段核心数据表。
- 第一阶段三组 API。
- Java 作为业务主系统。
- Python 通过 Tool API 访问 Java。
- Java 通过统一 Agent API 调用 Python。
- 第一阶段不做删除、复杂查询、权限、支付、退款、物流、售后和图片生成 API。

未进入实施计划前，还需要继续确认：

- 每个 API 的请求和响应字段。
- Java Entity 与 Python Pydantic Schema 的字段映射。
- `OperationPlanResult` 的完整 JSON 结构。
- `AgentRun` 的记录时机。
