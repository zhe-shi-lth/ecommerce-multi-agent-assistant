# 电商超级个体多 Agent 运营助手目标计划

## 1. 项目定位

本项目是一个面向市场就业的学习型工程项目，目标是构建一个面向小商家、个人卖家、独立站运营者的电商多 Agent 运营助手。

项目不定位为传统 Java 电商后台，也不定位为单纯的聊天机器人，而是定位为：

**Python 多 Agent 协同层 + Java 电商业务系统载体。**

核心思路：

- Python 多 Agent 是项目主要亮点。
- Java 系统提供商品、库存、采购、订单、出货、Agent 执行记录等业务能力。
- 第一阶段采用“大框架、小闭环”的策略：5 个 Agent 全部存在，但每个 Agent 的能力先轻量实现。
- 后续阶段逐步增强每个 Agent 的专业能力，例如产品图生成、库存预测、采购建议、订单履约、售后联动等。

确认项目名称：电商超级个体多 Agent 运营助手。

## 2. 就业目标

目标岗位方向：

- Java 后端工程师，具备 AI Agent 工程化能力。
- AI 应用开发工程师，具备企业系统集成经验。
- 电商 SaaS、跨境电商、智能客服、运营自动化、AI Agent 应用开发等方向岗位。

项目希望在简历中体现的能力：

- 能使用 Python 设计多 Agent 协同流程，而不是只会调用单个 LLM 接口。
- 能把 Agent 能力接入 Java 电商业务系统，形成真实业务闭环。
- 能处理 Agent 输出结构化、工具调用、执行记录、人工确认、失败降级等工程问题。
- 能从理论层面讲清楚多 Agent 为什么要拆分、如何协调、如何逐步增强。

推荐简历表达：

> 设计并实现电商超级个体多 Agent 运营助手，以 Python 构建多 Agent 协同层，支持商品运营、图片创意、库存补货、订单履约和流程总控；以 Java Spring Boot 提供商品、库存、采购、订单和出货等业务 API，实现从商品录入到运营建议、补货判断、出货判断和 Agent 执行记录落库的完整闭环。

## 3. 第一阶段范围原则

第一阶段不追求每个 Agent 做得很深，而是优先让多 Agent 框架站起来。

第一阶段原则：

- 5 个 Agent 必须全部存在。
- Supervisor Agent 先按固定流程编排，不做复杂动态规划。
- 每个子 Agent 都要有明确输入、结构化输出和执行记录。
- Agent 能力可以先用规则、模板或轻量 LLM 调用实现。
- Java 和 Python 的服务边界必须先打通。
- 第一阶段要能跑通一个小闭环，而不是堆很多零散能力。

第一阶段暂不做：

- 真实电商平台 API 接入。
- 真实支付、退款、售后系统。
- 真实图片生成服务。
- 复杂库存预测模型。
- 多店铺、多平台、多租户。
- 复杂权限系统。
- 完整前端管理台。

## 4. 总体架构

系统分为四层：

### 4.1 用户与业务入口层

第一阶段可以先通过 REST API 或简单页面发起运营任务。前端不是第一阶段重点。

职责：

- 录入商品基础信息。
- 录入库存、采购周期、模拟订单等基础数据。
- 触发 Agent 运营分析。
- 查看商品运营建议、图片创意建议、补货建议和出货建议。
- 查看每个 Agent 的执行记录。

### 4.2 Java 电商业务系统层

Java 侧作为企业业务系统载体，负责保存业务数据和提供 Agent 可调用工具。

第一阶段主要职责：

- 商品管理。
- 库存管理。
- 采购记录。
- 订单管理。
- 出货记录。
- Agent 执行记录。
- 人工确认记录，第一阶段可先做轻量状态字段。
- 暴露给 Python Agent 调用的业务 API。

确认技术栈：

- Java 21。
- Spring Boot 3.x。
- Spring Web。
- Spring Validation。
- Spring Data JPA。
- PostgreSQL。
- Flyway。
- Springdoc OpenAPI。
- Maven。

### 4.3 Python 多 Agent 协同层

Python 是项目核心层，负责 Agent 协同、运营判断、结构化输出和工具调用。

第一阶段确认采用 5 个 Agent：

1. Supervisor Agent。
2. Product Planning Agent。
3. Image Creative Agent。
4. Inventory & Purchase Agent。
5. Order Fulfillment Agent。

确认技术栈：

- Python 3.11+。
- FastAPI。
- Pydantic v2。
- LangGraph。
- LangChain 基础包。
- HTTPX。
- pytest。
- loguru。
- uv。

### 4.4 LLM 与工具层

LLM 是 Agent 的推理与生成能力来源。工具层负责把 Java 电商系统能力提供给 Agent 调用。

第一阶段工具示例：

- 查询商品详情。
- 查询库存。
- 查询采购记录。
- 查询订单。
- 保存 Agent 运营建议。
- 更新出货建议状态。
- 写入 Agent 执行记录。

工具调用原则：

- Agent 不直接操作数据库。
- Agent 通过 Java API 调用业务工具。
- Java 负责业务校验、状态保存和审计记录。
- Python 负责选择工具、组织参数和处理调用结果。

### 4.5 本地开发与服务通信

确认技术栈：

- 本地编排：Docker Compose。
- 数据库：PostgreSQL。
- 配置管理：`.env` 文件管理本地环境变量。
- API 文档：Java 使用 Springdoc OpenAPI，Python 使用 FastAPI 自动 OpenAPI。
- 第一阶段通信方式：同步 HTTP。
- Java 调 Python：Java 调用 Python Agent 服务的统一运营分析接口。
- Python 调 Java：Python 工具层调用 Java 暴露的商品、库存、订单、执行记录 API。
- 后续增强：框架稳定后再考虑消息队列、异步任务和更完整的可观测性。

## 5. 第一阶段业务闭环

第一阶段采用“小闭环”：

**商品录入 -> Agent 运营分析 -> 库存补货建议 -> 订单出货建议 -> 结果落库。**

流程细分：

1. 商家在 Java 系统中录入一个商品。
2. Java 系统保存商品基础信息，例如名称、类目、成本价、销售价、库存、采购周期。
3. Java 系统录入一条模拟订单。
4. 用户触发“生成运营建议”。
5. Java 调用 Python Supervisor Agent。
6. Supervisor Agent 创建本次执行上下文和 trace_id。
7. Product Planning Agent 生成商品标题、卖点、详情文案和上架建议。
8. Image Creative Agent 生成主图、场景图、营销图的图片创意说明或提示词。
9. Inventory & Purchase Agent 根据库存、订单数量、采购周期给出补货建议。
10. Order Fulfillment Agent 根据订单状态和库存判断是否可以出货。
11. Supervisor Agent 汇总 4 个子 Agent 的结构化结果。
12. Python 将汇总结果返回 Java。
13. Java 保存 Agent 执行记录和运营建议。
14. 用户查看本次 Agent 分析结果。

第一阶段完成标准：

- 5 个 Agent 全部参与一次完整执行。
- 每个 Agent 都有输入、输出、耗时、状态和错误信息。
- 每个 Agent 都输出结构化 JSON。
- Java 能保存商品、库存、订单和 Agent 执行记录。
- Python 能通过一个接口完成多 Agent 协同分析。
- 用户能看到一次完整的运营建议结果。

## 6. 第一阶段核心业务对象

第一阶段只保留 3 个核心业务对象：商品、库存、订单。这样能支撑 5 个 Agent 的完整协同，同时避免过早进入供应商、物流、售后、多店铺等复杂细节。

### 6.1 Product 商品

第一阶段字段：

- `product_id`：商品 ID。
- `name`：商品名称。
- `category`：商品类目。
- `description`：商品基础描述。
- `cost_price`：成本价。
- `sale_price`：销售价。
- `target_audience`：目标人群。
- `usage_scenario`：使用场景。
- `status`：商品状态，例如草稿、已分析、待人工确认。

### 6.2 Inventory 库存

第一阶段字段：

- `product_id`：商品 ID。
- `current_stock`：当前库存。
- `reserved_stock`：已占用库存。
- `safe_stock_threshold`：安全库存阈值。
- `purchase_cycle_days`：采购周期天数。
- `sales_last_7_days`：最近 7 天销量，第一阶段可以手填或模拟。
- `inventory_status`：库存状态，例如充足、偏低、缺货风险。

### 6.3 Order 订单

第一阶段字段：

- `order_id`：订单 ID。
- `product_id`：商品 ID。
- `quantity`：购买数量。
- `status`：订单状态，例如待分析、可出货、库存不足、需人工确认。
- `address_complete`：收货地址是否完整。
- `paid`：是否已付款。
- `manual_review_required`：是否需要人工确认。
- `fulfillment_suggestion_status`：出货建议状态。

第一阶段暂不单独建：

- 供应商表。
- 采购单表。
- 物流表。
- 售后表。
- 图片素材表。
- 平台店铺表。

## 7. 第一阶段 Agent 调用顺序与数据流

第一阶段采用固定顺序，不做复杂动态路由：

```text
Java Product + Inventory + Order
  -> Supervisor Agent
  -> Product Planning Agent
  -> Image Creative Agent
  -> Inventory & Purchase Agent
  -> Order Fulfillment Agent
  -> Supervisor Agent 汇总
  -> Java 保存 OperationPlanResult
```

整体输入：

```text
Product + Inventory + Order + trigger_type
```

整体输出：

```text
OperationPlanResult
```

第一阶段固定调用顺序的原因：

- 有利于学习多 Agent 基础结构。
- 有利于调试每个 Agent 的输入输出。
- 有利于先把 Java 与 Python 的服务边界打通。
- 等框架稳定后，再增强 Supervisor 的动态规划和路由能力。

## 8. 第一阶段 5 个 Agent 职责与输出

### 8.1 Supervisor Agent

定位：流程总控 Agent。

第一阶段职责：

- 接收 Java 传入的商品、库存和订单上下文。
- 创建 trace_id。
- 按固定顺序调用 4 个子 Agent。
- 汇总每个 Agent 的结构化输出。
- 生成最终运营建议摘要。
- 标记本次执行成功、部分失败或失败。

第一阶段输入：

- 商品信息。
- 库存信息。
- 订单信息。
- 业务触发类型，例如 `GENERATE_OPERATION_PLAN`。

第一阶段输出：

- `trace_id`：本次执行链路 ID。
- `product_plan`：Product Planning Agent 输出。
- `image_plan`：Image Creative Agent 输出。
- `inventory_plan`：Inventory & Purchase Agent 输出。
- `fulfillment_plan`：Order Fulfillment Agent 输出。
- `final_summary`：最终运营建议摘要。
- `manual_review_required`：是否需要人工确认。
- `errors`：错误列表。

后续增强：

- 动态规划执行步骤。
- 条件路由。
- 子 Agent 失败重试。
- 人工确认策略。
- 多轮任务执行。

### 8.2 Product Planning Agent

定位：商品运营规划 Agent。

第一阶段职责：

- 根据商品名称、类目、价格、目标人群生成商品标题。
- 生成 3 到 5 条商品卖点。
- 生成一段详情页文案草稿。
- 给出简单上架建议。

第一阶段输入：

- 商品名称。
- 商品类目。
- 成本价。
- 销售价。
- 商品基础描述。
- 目标用户，第一阶段可为空。

第一阶段输出：

- `recommended_title`：推荐商品标题。
- `selling_points`：商品卖点列表。
- `detail_description`：详情页文案草稿。
- `target_user_summary`：目标用户摘要。
- `listing_suggestion`：上架建议。

后续增强：

- 竞品分析。
- 平台 SEO 关键词。
- 小红书、抖音、淘宝、独立站等平台风格适配。
- A/B 文案生成。
- 转化率数据反馈优化。

### 8.3 Image Creative Agent

定位：产品图创意 Agent。

第一阶段职责：

- 根据商品信息生成图片创意方向。
- 生成主图提示词。
- 生成场景图提示词。
- 生成营销图提示词。
- 给出拍摄或设计建议。

第一阶段输入：

- 商品名称。
- 商品类目。
- 商品卖点。
- 目标人群。
- 使用场景。

第一阶段输出：

- `main_image_prompt`：主图提示词。
- `scene_image_prompt`：场景图提示词。
- `marketing_image_prompt`：营销图提示词。
- `image_style`：图片风格建议。
- `image_risk_notes`：图片风险提示，例如夸大宣传、侵权词、敏感元素。

后续增强：

- 接入图片生成模型。
- 接入图片审核。
- 主图质量评分。
- 批量生成不同平台尺寸。
- 图片与商品卖点一致性校验。

### 8.4 Inventory & Purchase Agent

定位：库存与采购建议 Agent。

第一阶段职责：

- 根据当前库存和模拟订单数量判断库存是否充足。
- 根据简单规则给出是否需要补货。
- 根据采购周期给出补货优先级。
- 生成采购建议。

第一阶段输入：

- 当前库存。
- 已占用库存。
- 订单数量。
- 采购周期天数。
- 安全库存阈值。

第一阶段输出：

- `inventory_status`：库存状态，例如充足、偏低、缺货风险。
- `should_restock`：是否建议补货。
- `suggested_restock_quantity`：建议补货数量。
- `restock_priority`：补货优先级。
- `reason`：判断原因。

后续增强：

- 销量预测。
- 季节性波动。
- 供应商比较。
- 安全库存模型。
- 采购成本优化。

### 8.5 Order Fulfillment Agent

定位：订单履约 Agent。

第一阶段职责：

- 根据订单状态和库存判断是否可以出货。
- 识别库存不足、订单异常、地址缺失等轻量风险。
- 给出出货建议。
- 标记是否需要人工确认。

第一阶段输入：

- 订单编号。
- 商品编号。
- 订单数量。
- 订单状态。
- 收货地址是否完整。
- 可用库存。

第一阶段输出：

- `can_ship`：是否可以出货。
- `fulfillment_status`：出货建议状态。
- `risk_flags`：风险列表。
- `manual_review_required`：是否需要人工确认。
- `next_order_status`：建议的下一步订单状态。

后续增强：

- 物流选择。
- 拆单。
- 异常订单识别。
- 售后联动。
- 仓库分配。

## 9. Java 系统第一阶段模块

第一阶段 Java 系统不做复杂电商后台，只做支撑 Agent 闭环的最小业务载体。

模块清单：

- 商品模块：保存商品基础信息。
- 库存模块：保存库存、占用库存、安全库存。
- 订单模块：保存模拟订单。
- 运营建议模块：保存 Supervisor 汇总结果。
- Agent 执行记录模块：保存每个 Agent 的输入、输出、状态、耗时和错误。
- 工具 API 模块：提供 Python Agent 可调用的查询和保存接口。

第一阶段状态设计：

- 商品状态：草稿、已分析、待人工确认。
- 订单状态：待分析、可出货、库存不足、需人工确认。
- Agent 执行状态：成功、部分失败、失败。

## 10. Python 服务第一阶段模块

第一阶段 Python 服务优先保证结构清晰。

建议模块：

- `app/api/`：FastAPI 接口。
- `app/agents/`：5 个 Agent 的实现。
- `app/schemas/`：Pydantic 输入输出模型。
- `app/services/`：Agent 编排服务。
- `app/tools/`：调用 Java API 的工具封装。
- `app/tracing/`：trace_id、日志和执行记录。
- `tests/`：单元测试和流程测试。

第一阶段核心接口：

- `POST /agent/ecommerce/operation-plan`

接口职责：

- 接收商品、库存和订单上下文。
- 执行 5 Agent 协同流程。
- 返回结构化运营建议。

## 11. 多 Agent 理论学习路线

理论学习必须服务于项目落地。每个理论主题都要能映射到项目中的一个模块或一个设计选择。

### 11.1 Agent 基础

学习目标：

- 理解 LLM、Agent、Workflow、Tool Calling 的区别。
- 理解为什么企业项目不能只依赖自由对话式 Agent。
- 理解 Agent 的输入、输出、状态和工具边界。

项目映射：

- Product Planning Agent 和 Image Creative Agent 偏内容生成。
- Inventory & Purchase Agent 和 Order Fulfillment Agent 偏业务判断。
- Supervisor Agent 偏流程控制。

### 11.2 多 Agent 协同

学习目标：

- 理解按职责拆分 Agent 的原因。
- 理解集中式协调和去中心化协作的区别。
- 理解 Agent 之间如何传递上下文和结构化结果。

项目映射：

- 第一阶段采用集中式 Supervisor 协调。
- 子 Agent 不互相直接对话，统一由 Supervisor 编排。
- 每个 Agent 的输出都进入最终运营建议。

### 11.3 工具调用

学习目标：

- 理解工具是 Agent 影响真实系统的边界。
- 理解工具调用需要参数校验、权限控制、超时、失败记录和审计。
- 理解 Agent 不应该绕过 Java 业务系统直接操作数据库。

项目映射：

- Python 工具层通过 HTTP 调用 Java API。
- Java 保存商品、库存、订单和执行记录。
- Python 负责选择工具和组织参数。

### 11.4 结构化输出

学习目标：

- 理解企业系统不能依赖纯自然语言结果推进流程。
- 学习使用 Pydantic 或 JSON Schema 约束 Agent 输出。
- 学习输出校验失败后的重试、降级和人工确认。

项目映射：

- 每个 Agent 都输出结构化 JSON。
- Supervisor 输出统一结果对象。
- Java 根据结构化字段保存结果。

### 11.5 可观测性与评估

学习目标：

- 理解 Agent 系统需要追踪每一步输入、输出、耗时、错误和决策依据。
- 理解评估不仅是模型回答好不好，还包括流程是否正确、工具是否安全、结果是否可复现。

项目映射：

- 每次执行都有 trace_id。

## 13. 技术边界与原则

项目开发原则：

- Python 多 Agent 是主线，Java 是企业业务系统载体。
- 第一阶段做大框架、小闭环，不追求单个 Agent 深度。
- 5 个 Agent 第一阶段全部存在。
- 每个 Agent 都必须有明确输入、输出和职责边界。
- Agent 输出必须结构化，不能只返回自然语言。
- 工具调用必须经过 Java API，不直接绕过业务系统。
- 高风险动作可以先标记人工确认，后续再实现完整人工确认流程。
- 每一次 Agent 执行都要能追踪输入、输出、耗时、状态和错误。
- 先做同步 HTTP 闭环，后续再考虑消息队列。

## 15. 面试讲解路径

面试时建议按下面顺序讲：

1. 先讲业务问题：小商家和个人卖家在商品上架、图片创意、库存补货和订单出货上存在大量重复决策。
2. 再讲架构选择：Java 负责稳定业务数据和工具 API，Python 负责多 Agent 智能协同。
3. 再讲多 Agent 分工：Supervisor、Product Planning、Image Creative、Inventory & Purchase、Order Fulfillment。
4. 再讲第一阶段策略：先做大框架和小闭环，5 个 Agent 全部参与，能力逐步增强。
5. 再讲工程难点：结构化输出、工具调用边界、执行记录、失败降级、人工确认。
6. 最后讲扩展方向：图片生成、库存预测、供应商选择、物流异常、售后联动、可观测性。

重点表达：

> 这个项目不是把大模型接到电商后台里，而是把 Python 多 Agent 作为电商运营自动化的智能协调层。Java 提供商品、库存、订单和出货等业务事实与执行能力，Python Agent 负责商品运营规划、图片创意、库存补货、订单履约判断和流程总控。第一阶段采用大框架、小闭环策略，让 5 个 Agent 全部参与一次完整业务流，再逐步增强每个 Agent 的专业能力。
